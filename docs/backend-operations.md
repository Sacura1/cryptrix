# Backend operations

The backend can be developed and verified entirely locally. Practice mode uses simulated amounts and local strategy bots; no Arc deployment or model credential is required. Paid mode uses real receipt verification and a separately configured signer. It has no simulated-funding fallback.

## Local commands

From `cryptrix/`, run `npm run setup`, `npm run check`, `npm run contracts:compile`, `npm run build`. Start the API with `npm start`, or use `npm run dev` while developing. Configuration lives in `backend/.env`; start with `backend/.env.example`. Dependencies, generated contracts, databases and compiled code live under `backend/`.

Public `/health` reports process liveness, `/ready` reports worker readiness, and `/config` gives the frontend the configured chain, stakes, hosted capabilities and trust disclosures. Configure `FRONTEND_ORIGINS` explicitly. Spectator snapshots and SSE remain public. Streams retain browser CORS headers and close during shutdown.

## Private signing service

Use `backend/.env.signer.example` as the reference for a separate `backend/.env.signer`. For a new deployment, generate a random service credential of at least 32 characters and a separate 32-byte base64 encryption secret through your secrets manager. For the existing Arc deployment, preserve the signer database, namespace and encryption secret as described in [the Koyeb guide](koyeb-deployment.md). The API receives the service credential, never the encryption secret. Owner and deployer private keys are never imported into this service.

Run `npm run signer` for development, or `npm run build` followed by `npm run signer:start`. Without deployment addresses, authenticated key-address lookup works, but transaction signing is refused. This allows obtaining the resolver's public address before deploying an escrow with that immutable resolver. Deployments must use separately approved owner/deployer wallet tooling.

The key and signing protocol is authenticated; GET /health is a public boolean readiness check:

| Method and path | Purpose |
| --- | --- |
| `GET /v1/keys/resolver` | Stable public resolver address |
| `GET /v1/keys/keeper` | Stable public refund-keeper address |
| `GET /v1/keys/agent:<agent UUID>` | Stable restricted agent signing address |
| `POST /v1/transactions` | Sign an exact bounded transaction and immutable operation ID |

There is no owner-key import/export, arbitrary execution or user withdrawal endpoint. Keys are generated by the service and encrypted with AES-256-GCM. Each prepared transaction is stored before returning its signature. Reusing an operation ID with different inputs fails. Nonces and fee reservations are unique and durable.

Agent keys can call only the fixed factory account's equipment-bound create/join methods under its current owner-granted policy. Keeper keys can cancel eligible expired escrow matches and claim credits into verified original factory accounts; they cannot redirect funds. The resolver independently reconstructs a complete replay and checks funded entrants, rules, equipment, ranks and payouts before signing settlement. This consistency check does not prove operator honesty or unbiased seed selection.

Each service key pays its own Arc gas. Limits are 500,000 gas per transaction, maximum fee 20–100 Gwei, and 1 USDC of conservative native-gas reservations per UTC day per key. This is a service-funded direct-call design; agent-account funds are never debited for service gas. Fund those public key addresses separately. Reservation exhaustion stops signing rather than charging an owner account or silently raising a ceiling.

Production must put the signer in a separate OS/container identity and private network, with independent filesystem access, encrypted volumes, secrets and restricted egress. Two processes under the same desktop account provide development separation only. Use HTTPS between different hosts; loopback HTTP is accepted locally. Do not expose the signer publicly. Restrict NTFS ACLs on Windows; Unix file mode alone does not establish Windows access control.

## Paid configuration and ownership flow

After separately deploying reviewed contracts, configure `MATCH_MODE=paid`, the intended `ARC_NETWORK`, `ESCROW_ADDRESS`, `AGENT_ACCOUNT_FACTORY`, `ESCROW_DEPLOYMENT_BLOCK`, and RPC URL. Configure `SIGNER_URL` and `SIGNER_TOKEN` together. Hosted automation also requires `HOSTED_DECISIONS=model`, an explicit compatible `HOSTED_MODEL` and provider credential. `npm run arc:check` performs read-only chain, token, version and factory checks; it never submits a transaction.

An owner creates their factory account, registers it, funds it, obtains `/agents/:id/signer`, and signs a bounded authorization plan for that address. Enabling automatic entries verifies that the current account policy authorizes the signer. Platform limits remain additional constraints. Stopping automatic entries pauses future entry broadcasts; active decisions, settlement and refunds continue. Revoking on-chain policy independently prevents future delegated spending. A model-disabled configuration also pauses hosted paid entry jobs.

## Persistence and recovery

SQLite uses WAL, full synchronization, additive schema migrations and a future-version guard. Match state, entry intents, usage, locked actions, provider call claims, index cursors, transaction bytes and audit state are persistent. Instances sharing the same local database use a leased match clock, per-call claims, indexer leases and fenced payment jobs. This does not turn SQLite into a distributed database; never place it on an unsupported network filesystem. Production uses the Neon changeset/checkpoint journal and one fenced writer per namespace; local SQLite files are temporary with DATABASE_URL configured. See [Neon durability](postgres-readiness.md) and [Koyeb hosting](koyeb-deployment.md). Load-test capacity before adding coordinators; identical namespaces cannot have simultaneous writers.

Payment operations reserve the unsigned transaction and nonce before asking the signer, then persist the exact signed bytes and hash before broadcast. A lost RPC reply is recovered by receipt lookup or rebroadcasting those identical bytes. It never creates another entry signature automatically. Successful receipts are reconciled against contract state; backend `finished` and chain `settled` remain separate states. Replay or on-chain-result mismatches stop confirmation and require investigation.

Indexing begins at the configured escrow deployment block, commits each canonical log and cursor atomically, records directly submitted transactions, and checks the cursor block hash on restart. A changed history, RPC head behind the cursor, malformed log or reconciliation failure prevents a healthy index status. Do not reset a cursor to hide a financial inconsistency.

Direct entrants into a platform-created offer are reconstructed in canonical order. Legacy default gear can be recovered. Custom/salted gear requires the funded wallet to register and reveal its matching commitment before play starts. API-created intents persist a fresh random equipment salt privately; the completed replay discloses it for verification. A passive reconstructed identity can be adopted after wallet ownership proof. Games created entirely outside this platform have no platform seed/engine state: the public chain ledger records them as `managed:false`; they remain subject to their contract deadlines and refunds. Never invent a replay or settle them as platform games.

Payouts and refunds are escrow credits until claimed. Owner claim plans return credits to the original account. Claims are aggregate account events; the backend does not pretend to allocate a claim transfer to a particular match. A restricted keeper automatically claims hosted winnings/refunds into the original factory account. Withdrawals always require its immutable owner. External participants retain their own claim flow.

## Monitoring and operator actions

Set a separate `OPS_TOKEN` of at least 32 characters. Authenticated `/ops/status`, `/ops/jobs` and `/ops/audit` expose worker success times, failure codes, cursor progress, job counts and sanitized events. They never expose raw signatures, private payloads, owner tokens or model prompts. Monitor readiness, stale clock/indexer status, retry counts, unsettled games approaching their deadline and exhausted signer/provider budgets.

`POST /ops/jobs/retry` with `{ "key": "..." }` can requeue a pending or reviewed unexpired operation without changing its payload, nonce or signature. First resolve the cause. Expired or uncertain signed operations require receipt/pending-nonce reconciliation and human review; the endpoint refuses blind retries. Do not delete nonce records or replace signatures to unblock a queue. Advanced nonce replacement/cancellation procedures must be reviewed before production operations rely on them.

On a signer compromise, stop new entries, revoke affected account policies through owner wallets, preserve the audit trail, and investigate bounded spending already committed. Revocation does not cancel games already funded. On resolver compromise, halt entry admission and use the escrow's deadline refund path; the immutable resolver cannot be silently replaced. A new reviewed escrow is needed for a new resolver.

## Encrypted backups

**Neon deployments:** back up the PostgreSQL state/journal together using database snapshots or reviewed exports. Preserve the existing signer encryption secret independently. The local SQLite backup command refuses to run with DATABASE_URL or SIGNER_DATABASE_URL set because it would otherwise export an obsolete local file. Do not restore a local SQLite file by changing DATABASE_PATH while Neon mode is active.

**SQLite-only local mode:** use a separate `BACKUP_ENCRYPTION_KEY` containing 32 random base64-encoded bytes. From the root:

```sh
npm run backup -- create ./data/backups/platform.enc
npm run backup -- restore ./data/backups/platform.enc ./data/restored-platform.sqlite
```

Forwarded paths are relative to `backend/`. Creation opens the source database read-only and takes a consistent SQLite backup, including WAL state, before encrypting it with authenticated AES-256-GCM. Restore authenticates before writing plaintext, requires a new destination, and checks database integrity/version. Existing databases and backups cannot be overwritten. This local implementation caps backups at 128 MiB; use a reviewed streaming backup service above that size.

Back up the signer database separately by supplying its file as `DATABASE_PATH` to the same backup command. The read-only backup command does not migrate or add platform tables to the signer database. Retain the signer encryption secret in a separate protected recovery system; losing it makes its encrypted service keys unrecoverable. Keep the backup encryption key separate from the backup files. The API database also contains private game state, so protect its live volume.

Before restoring, stop the API, decision worker, payment worker and signer, retain the current files, and restore each database to a new path. Restore a consistent platform/signer pair, configure their paths, and reconcile all signed operations with on-chain receipts/nonces before resuming admission. A stale backup must never trigger a second provider call or financial transaction. Test restore drills without real funds first.

## Launch checks outside local completion

Arc testnet deployment, funded hosted/external entries, native/ERC20 amounts, fees, settlement, claims and owner withdrawal/revocation have passed. Blocklist failures, browser/passkey recovery and production restore/capacity drills remain launch checks. Measure real same-model competition, inference cost, latency and capacity with explicit provider limits. Obtain an independent contract/service security review. Review resolver governance, dispute handling and randomness/private-state assumptions. Then deploy mainnet through a separately authorized, recorded process. A separate live-model test also passed earlier. Mainnet and Koyeb are not deployed; the testnet integration is not an audit or a production-capacity certification.
